# Changelog

Alle nennenswerten Änderungen an SmartCodeReview. Die Versionen folgen [Semantic Versioning](https://semver.org/lang/de/); wie das hier ausgelegt wird und wie man ein Release macht, steht in [docs/08-versionierung.md](docs/08-versionierung.md).

Docker-Images: `culmi/smart-code-review:<version>` und `:latest` (= letztes Release).

## [Unreleased]

### Neu
- **Commits:** Die Commits des PR/MR stehen im Review-Fenster (Tab *Commits*) und auf der Übersicht, mit Fortschritt pro Commit. Jede geänderte Zeile ist dem Commit zugeordnet, der sie zuletzt geschrieben bzw. entfernt hat (`commits.json`, API `GET …/commits`).
- **Nur einen Commit ansehen:** Ein Klick auf einen Commit filtert alle Ansichten (Kategorien, Flows, Dateien, Übersicht) auf seine Änderungen. Änderungen anderer Commits sind im Code abgeblendet, Häkchen, «Block ok» und Fortschritt beziehen sich nur auf die Zeilen des Commits. In der Toolbar geht es mit ← → von Commit zu Commit; der Commit steht auch in der URL.
- **Ganzes Repository analysieren:** Repository-URL ins Suchfeld oder Ordner-Knopf in der Toolbar eines PRs: Alle Dateien des Default-Branches werden wie ein Pull Request analysiert, in dem jede Datei neu ist (Kategorien, Flows, Komponenten, Tests, Commit-Filter, Blame). Geladen wird ein einziges Archiv; Commits sind die letzten 50 des Branches. API: Nummer `0`, z. B. `GET /api/prs/github/owner/repo/0`.
- **Annotieren mit Git Blame:** Toolbar-Knopf blendet in allen Code-Blöcken eine Blame-Spalte ein (wie in IntelliJ): Datum bzw. Uhrzeit, Autor, Nummer des PR-Commits, ältere Zeilen blasser. Gelöschte Zeilen zeigen den Commit, der sie entfernt hat. Klick filtert auf den Commit. GitHub über GraphQL, GitLab über die Blame-API; Cache unter `blame/` (API `GET …/blame?path=…`).
- **Halb akzeptiert:** Eine Zeile, die an mehreren Orten vorkommt (mehrere Kategorien, Flows) und an einem Ort akzeptiert wurde, erscheint an den anderen Orten als «halb akzeptiert»: halbes Häkchen, Hinweis «bereits an anderem Ort akzeptiert» (Klick springt dorthin, Tooltip nennt die Orte). Mehrere akzeptierte Orte werden einzeln geführt; das Zurücknehmen an einem Ort lässt die anderen stehen. Halb akzeptiert zählt im Fortschritt noch nicht.
- **Beschreibung jeder Kategorie:** Unter dem Titel («Wie entsteht diese Kategorie?») und als Tooltip in der Übersicht steht, wie die Kategorie aufgebaut ist und wie sie in Gruppen unterteilt wird. Aus den Regeln abgeleitet, in `rules.json` pro Kategorie mit `builds` / `divides` überschreibbar.
- **Abdeckung des geänderten Codes:** Die Kategorie Tests zeigt über der Testübersicht, welche geänderten Funktionen ein geänderter Test direkt erreicht, welche nur indirekt (über anderen geänderten Code) und welche gar nicht – gruppiert «Ohne Test», «Nur indirekt getestet», «Direkt getestet», mit Anzahl Verzweigungen und geänderten Zeilen, sortiert nach Risiko. Klick springt zum Code bzw. zum Test. Ändert ein PR keinen Test, führt die Kachel auf der Übersicht (und «Abdeckung» im Review-Baum) auf eine eigene Seite. Code-Blöcke testbarer Funktionen tragen ein Abzeichen «ohne Test», «nur indirekt getestet» oder «n Tests». Statisch ermittelt (`analysis.json` → `coverage[]`); welche Kategorien Tests brauchen, steht in `rules.json` (`needsTests` an der Kategorie).
- **Spezifikation (Testnamen):** Ganz oben in der Kategorie Tests stehen die Testnamen jeder geänderten Testdatei als Gliederung (Suite › Suite › Test), verglichen mit der Basisversion: neu (+), geändert (~), umbenannt (→, mit «vorher: …»), entfernt (−, durchgestrichen); unveränderte Tests sind blass und hinter «n unveränderte anzeigen» versteckt. Darüber eine Zusammenfassung wie «+6 neu · ~2 geändert · →1 umbenannt · −1 entfernt · 14 unverändert». Klick springt zum Testcode, ein entfernter Test öffnet die Dateiansicht bei den gelöschten Zeilen. JUnit-Testklassen und `@Nested`-Klassen gelten als Suites. Dafür wird die alte Version geänderter Testdateien geladen (`sources-base/`); fehlt sie, zeigt die Gliederung nur die neue Seite. Deterministisch, ohne KI (`analysis.json` → `specs[]`).
- **Geänderte Erwartungen:** Der Spec-Diff vergleicht bei bestehenden Tests die Assertions alt gegen neu und warnt, wenn ein PR Tests an den Code anpasst: «Erwartung geändert» (gleicher Gegenstand, anderer Wert, z. B. `toBe(9)` → `toBe(6)`, `assertEquals(201, …)` → `assertEquals(200, …)`), «Assertion entfernt», «abgeschwächt» (z. B. `toEqual('Ann')` → `toBeTruthy()`), «deaktiviert» (`xit`, `it.skip`, `xdescribe`, `@Disabled`, `t.Skip` – auch über die Suite) und «3 → 1 Assertions». Ein Klick auf die Markierung zeigt alte (durchgestrichen) und neue Anweisung mit Zeilennummer, ein Klick auf eine Zeile springt in den Testcode. Zusammenfassung, Dateikopf und die Kachel der Tests auf der Übersicht zeigen «⚠ n Erwartungen geändert · m deaktiviert», Code-Blöcke solcher Tests ein Abzeichen. Musterbasiert, in `rules.json` anpassbar (`assertions`, `weakAssertions`, `disabledTests`); `analysis.json` → `specs[].entries[].expectations`, `assertionsBefore`, `assertionsAfter`, `disabled`. Jasmine/Jest `xit`/`xdescribe`/`fit` werden jetzt auch als Testfälle erkannt (`Analyzer.VERSION` 18).
- **Test-Steckbrief:** In der Testübersicht steht unter jedem Testnamen eine Zeile wie «Fehlerfall · Integration · 3 Assertions (Gleichheit, HTTP) · Mocks: PlayerRepository, HTTP · 4 Fälle»: Fall (Fehlerfall, wenn der Test ein Scheitern erwartet – `assertThrows`, `.toThrow`, HTTP-Status ≥ 400, Fehlermeldung, oder der Name sagt es; Grenzfall bei leeren/`null`-/Grenzwerten als Eingabe des geprüften Codes – Argumente der Aufrufe des getesteten Codes und von HTTP-Anfragen sowie Parameterquellen, nicht Testdaten oder erwartete Werte; sonst Normalfall), Ebene (Unit, Integration, E2E aus Annotationen wie `@QuarkusTest`, RestAssured, Testcontainers und Pfad), Anzahl und Art der Assertions, ersetzte Abhängigkeiten (Mockito, Jasmine/Jest/Vitest, Angular-Provider, Go-Fakes; gemocktes Backend = «HTTP») – auch aus Feldern, Setup und umschliessenden Suites – und die Anzahl parametrisierter Fälle (`@ValueSource`, `@CsvSource`, `it.each`, Go-Tabellentests). Jeder Teil erklärt im Tooltip, woran er erkannt wurde. Standard ist die Tabelle: alle Tests als sortierbare Tabelle (Test, Prüft, Fall, Ebene, Assertions, Mocks, Fälle) mit einer Zusammenfassung wie «14 Tests · 9 Normalfall, 4 Fehlerfall, 1 Grenzfall · 11 Unit, 3 Integration · 2 parametrisiert (9 Fälle)»; ein Klick auf einen Teil filtert, ein Klick auf eine Zeile springt zum Test. Musterbasiert, in `rules.json` anpassbar (Abschnitt `testProfile`); `analysis.json` → `tests[].profile`. Nebenbei erkannt: mehrzeilige Annotationen (`@CsvSource({ … })` über einem `@ParameterizedTest`), Java-Text-Blöcke (`"""…"""`) als Strings und `it.each`/`test.each` mit mehrzeiliger Tabelle als Testfälle (`Analyzer.VERSION` 19).
- **Fallmatrix (ähnliche Tests):** In der Kategorie Tests steht zwischen «Spezifikation» und «Abdeckung» eine Tabelle Eingabe → Erwartung für fast gleiche Tests (kopiert, ein Wert geändert) und für parametrisierte Tests: Tests derselben Suite, deren Eingabecode bis auf Literale gleich ist, werden zu einer Matrix – die unterschiedlichen Literale sind die Eingabespalten (z. B. `putJerseyNumber(…) Arg 1`), die Assertions nach Gegenstand ausgerichtet die Erwartungsspalten (`statusCode`, `jerseyNumber`); `@ValueSource`/`@CsvSource`/`@EnumSource`/`@NullSource`, `it.each` (Array, Objekte, Template-Tabelle) und Go-Tabellentests mit ihren Zeilen (Erwartung nach Spaltenname oder Verwendung nur in Assertions). Zusammenfassung wie «3 Matrizen · 14 Fälle · 1 doppelt», pro Matrix eine aufklappbare Vorlage mit den Spalten als ‹1›, ‹2› …, ein Trennstrich zwischen Eingabe und Erwartung, unter jeder Eingabespalte die abgedeckten Werte («geprüft: 0, 7, 23, 150»). Derselbe Fall zweimal ist in Warnfarbe markiert («gleicher Fall wie …», bei anderer Erwartung «gleiche Eingabe, andere Erwartung als …») – auch gegen unveränderte Tests derselben Datei. Ein Klick auf eine Zeile springt zum Test. Token-basiert, Spaltenrollen in `rules.json` anpassbar (Abschnitt `caseMatrix`); `analysis.json` → `caseMatrices`. Nebenbei: Strings über mehrere Zeilen (Text-Blöcke, Template-Strings) werden im Steckbrief jetzt mitgelesen, `test.each` mit Template-Tabelle umfasst den ganzen Testrumpf, und ein destrukturierter Callback `({ a, b }) =>` ist kein Testrumpf mehr (`Analyzer.VERSION` 20).
- **Bestehende Tests nachladen:** Bisher zählten in der Abdeckung nur Tests, die der PR ändert – Code, den ein bestehender Test schon prüft, stand fälschlich unter «Ohne Test». Jetzt werden zu jeder geänderten Datei die passenden bestehenden Testdateien nach Namenskonvention gesucht (`X.spec.ts` daneben, `XTest.java` im gespiegelten Ordner `src/test/…`, sonst der nächstgelegene gleichen Namens, dazu z. B. `XSecurityTest`), am Head des PRs geladen und wie geänderte Tests mit dem Code verknüpft. Neue Gruppe «Nur durch bestehende Tests» in der Abdeckung, bestehende Tests als eigene, gestrichelte Chips mit `datei:zeile` (Tooltip: warum geladen) – auch bei direkt getesteten Funktionen, damit man sieht, welche alten Tests durch die Änderung laufen. Unter dem Titel steht die Grundlage («geänderte Tests im PR + 2 nachgeladene Testdateien (Namenskonvention)»), mit Warnung, wenn das Limit (30 Dateien, `rules.json` → `relatedTests`) abgeschnitten hat. Code-Blöcke tragen «durch bestehende Tests», die Kachel auf der Übersicht zählt mit. `analysis.json` → `existingTests[]`, `relatedTests`, `coverage[].existingTests`; Auswahl in `related.json`, Dateien unter `sources-related/`, `structure.json` enthält jetzt alle Dateipfade (ältere werden einmal neu gelesen) (`Analyzer.VERSION` 21).
- **Mock-Grenzen im Flow:** Ein Flow zeigt jetzt, welche Schritte die Tests wirklich ausführen. Erreicht ein Test Code einer Abhängigkeit, die er mockt (`@Mock`/`@InjectMock`, `{ provide: X, useValue }`, `createSpyObj`, `vi.mock` …), läuft dort nur der Mock: Die Verknüpfung hält an, und nur gemockt erreichter Code zählt in der Abdeckung nicht (Chip «Mock»). Knoten im Flow-Diagramm sind eingefärbt – echt getestet, nur gemockt, nicht erreicht (Legende, Tooltip mit den Tests und «gemockt in …») –, Verbindungen durchgezogen, wenn ein Test hindurchläuft, fein gestrichelt «einzeln», wenn beide Seiten nur getrennt getestet sind (typisch der REST-Sprung zwischen Frontend und Backend), sonst blass. Tests, die eine **geänderte** Funktion mocken und beim Namen stubben (`setJerseyNumber: jest.fn(…)`, `when(repo.save(…))`, `spyOn(api, 'm')` …), halten ihr altes Verhalten fest: Sie stehen in der Kategorie Tests unter «Mocks auf geändertem Code» (Klick springt zur Stub-Zeile), ihr Code-Block trägt «mockt geänderten Code», der gemockte Schritt im Flow ein Warnzeichen. Namensbasiert, in `rules.json` anpassbar (`testProfile.mockMembers`); `analysis.json` → `mockWarnings[]`, `flowCoverage[]`, `tests[].covers[].mocked`, `coverage[].mockedTests` (`Analyzer.VERSION` 22).
- **Fall- und Effekt-Abgleich:** Die Abdeckung zeigt pro geänderter Funktion nicht nur, *ob* ein Test sie erreicht, sondern welche Fälle und Wirkungen des Codes die Tests prüfen, die sie wirklich erreichen (ohne Mocks): Fehlerausgänge (`throw new NotFoundException(…)` – erwartet ein Test den Typ oder den HTTP-Status 404?), Grenzen (`x < 1`, `x <= MAX` mit `MAX = 99` – sind 1 und 99 unter den Testeingaben?), Wirkungen geänderter Zeilen (gesetzte Felder, Speichern, Ereignisse, HTTP-Aufrufe – nennt eine Assertion das Feld oder verifiziert den Aufruf?) und ein Hinweis bei mehr Verzweigungen als Tests. Unter jeder Funktion eine Kurzzeile wie «⚠ NotFoundException ungeprüft · Grenze 1…99: 1, 99 fehlen · jerseyNumberChangedAt ungeprüft», aufklappbar zur ganzen Liste mit den prüfenden Tests; ein Klick springt zur Codezeile. Funktionen mit offenen Fällen sind markiert, auch unter «Direkt getestet»; der Kopf fasst zusammen («7 offene Fälle in 4 Funktionen»). Im Code steht ein Chip auf der Zeile («kein Test erwartet NotFoundException», «Grenze nicht geprüft: 1, 99», «Wirkung ungeprüft: jerseyNumberChangedAt»), unter einer Fallmatrix die Grenzen des Codes, die ihr fehlen. Muster im neuen Regel-Abschnitt `caseCheck` (z. B. Ausnahme → HTTP-Status). Analysen werden neu berechnet.
- **Erwartungs-Regeln:** Regeln der Form «wenn X geändert wird, braucht es einen Test der Form Y» werden pro PR geprüft. Eingebaut: geänderte Berechtigungsprüfung (`@RolesAllowed`, `@PreAuthorize`, `access.require…(`, Guards …) → Test für den verweigerten Zugriff (401/403 oder `AccessDeniedException`); neuer Endpunkt → Test über HTTP (RestAssured auch mit Pfadparametern, MockMvc, supertest, Playwright …; `HttpTestingController` zählt nicht, das Backend ist dort gemockt); geänderte Validierung (`@Min`, `@Size`, `Validators.required` …) → Fehler- oder Grenzfall-Test; geändertes `@Transactional` → Integrationstest; geänderter Message-Listener → Test, der ihn aufruft. Es zählen Tests, die den Code wirklich erreichen (ohne Mocks), bei Endpunkten auch Tests, die ihn über HTTP aufrufen. In der Kategorie Tests steht die Box «Erwartete Tests (Regeln)» – nicht erfüllte zuerst mit Hinweis, erfüllte eingeklappt mit den Tests, ein Klick springt zur auslösenden Zeile –, im Code ein Chip «Regel: Test für den verweigerten Zugriff (401/403) fehlt», auf der Übersicht die Zahl der nicht erfüllten Regeln. Eigene Regeln in `rules.json` (Abschnitt `testRules`, nach Id eingemischt; `"enabled": false` schaltet eine eingebaute ab). `analysis.json` → `ruleChecks[]` (`Analyzer.VERSION` 24).
- **Test-Smells:** Geänderte Tests, deren Wert zweifelhaft ist, werden markiert, damit man dort zuerst hinschaut: keine Assertion (`verify`, `expectOne`, `toHaveBeenCalled` zählen als Assertion), nur schwache Assertions (`toBeTruthy`, `assertNotNull` …), fokussiert (`fit`, `fdescribe`, `.only`: die CI führte nur diese aus), feste Wartezeit (`Thread.sleep`, `time.Sleep`; `setTimeout`/`sleep` nur ohne Fake-Timer), der Test mockt die getestete Einheit selbst (Mock oder Spy, z. B. `jest.spyOn(view, 'save')` bei `view.save(…)`) und neue, ausgeschaltete Tests. In der Testübersicht stehen die Smells als Warn-Chips und in der Spalte «Smells» der Tabelle, die Zusammenfassung «n Tests mit Smells» filtert darauf; im Test-Block ein Abzeichen «Smell: keine Assertion» im Kopf und ein Chip auf der Zeile, auf der Übersicht die Zahl in der Kachel der Tests. Muster im Regel-Abschnitt `testSmells` (je Art abschaltbar mit `"enabled": false`). `analysis.json` → `tests[].smells[]` (`Analyzer.VERSION` 25).
- **Wirkung von Setup und Testdaten:** Ein geändertes `beforeEach`, eine `@BeforeEach`-Methode, eine gemeinsame Fixture (`const CARMELA = {…}`, ein Feld mit Wert) oder eine Testhilfe (`TestData.player(…)`, `playerWithNumber(…)`) ändert still die Bedeutung von Tests, die nicht im Diff stehen. Pro geändertem Stück zeigt die Spezifikation der Tests jetzt, auf welche Tests es wirkt – ein Setup-Block auf seine Suite bzw. Klasse (auch verschachtelte, `@Nested` und Unterklassen), eine Fixture oder Hilfe auf alle Tests, die sie direkt, über ihr Setup oder über andere Hilfen nennen, auch in anderen Testdateien mit Import und in den nachgeladenen bestehenden Tests: «Testdaten geändert: CARMELA wirkt auf 17 Tests, davon 3 unverändert», aufklappbar, Klick springt zum geänderten Code. Gewarnt wird nur, wenn unveränderte Tests betroffen sind; diese bleiben in der Gliederung sichtbar und tragen «Setup geändert». Der Block des Stücks trägt «wirkt auf 17 Tests (3 unverändert)», die Kachel der Tests auf der Übersicht «Setup/Testdaten geändert: wirkt auf n unveränderte Tests». JUnit-Methoden mit `@BeforeEach`, `@AfterAll` … gelten jetzt als Setup-Blöcke. Test-Hilfsdateien ausserhalb der Testpfade im Regel-Abschnitt `setupImpact.supportPaths`. `analysis.json` → `setupImpacts[]` (`Analyzer.VERSION` 26).
- **Commit-Bezug der Tests:** Die Reihenfolge der Commits verrät, was der endgültige Diff versteckt. An den Commits stehen jetzt Chips: «passt Erwartungen an», wenn eine Assertion eines im PR geschriebenen Tests erst in einem späteren Commit geändert wurde (Warnung, wenn dieser Commit nur Tests ändert oder «fix tests», «Tests anpassen» … heisst, sonst Info), «Fix ohne Test», wenn ein Commit mit Fix-Titel (`fix`, `bug`, `hotfix`, `korrigiert` …) Code, aber keinen Test ändert, und «Logik ohne Test» (Info), wenn ein Commit testbaren Code ohne Test ändert und auch kein späterer Commit einen Test dafür nachreicht. In der Spezifikation der Tests trägt ein solcher Test «Erwartung nachträglich in 406522a «fix tests» geändert» (Klick springt zur Assertion), im Code steht ein Chip auf der Assertion-Zeile (Klick zeigt nur diesen Commit), auf der Übersicht bei «Commits» die Zahl der Hinweise. Merge-Commits und Seitenzweige werden übersprungen. Muster im neuen Regel-Abschnitt `commitChecks`; `commits.json` → `findings[]`, bei jedem Abruf aus der Zuordnung und der aktuellen Analyse neu berechnet (die Analyse selbst bleibt unverändert).

### Geändert
- **Kategorien sind Module** mit einheitlicher Schnittstelle (`CategoryModule`); Hinzufügen oder Entfernen einer Kategorie beeinflusst die anderen nicht. Datenflüsse bleiben als Ausnahme mit eigener Ansicht (`view: "flow"`). Vorbereitet, aber noch nicht umgesetzt: Kategorien von aussen hinzufügen (siehe Roadmap).
- **Abdeckung:** Datenbank & Migrationen (`persistence`) braucht wieder Tests – Logik in Entities (z. B. `Player.isJerseyNumberTaken`) erscheint in der Abdeckung. Dafür fehlen in allen Kategorien triviale Getter und Setter (Rumpf nur `return x;` bzw. `this.x = x;`).
- Die Regeln für Zeilen an mehreren Orten stehen an einer Stelle (`LineAcceptance`) statt doppelt in Backend und UI verstreut. Dateiformat von `review.json` unverändert.
- `Analyzer.VERSION` 14: Analysen enthalten pro Kategorie `builds`, `divides`, `view`, `origin`; gespeicherte Analysen werden neu berechnet.
- **Dokumentation für Architekt:innen:** Architektur-Überblick mit Diagrammen, Laufzeitsichten und Architekturentscheiden ([docs/09](docs/09-architektur-ueberblick.md)), alle Funktionen als Anforderungen mit Nachweis ([docs/10](docs/10-anforderungen.md)), belegte Verbesserungsmöglichkeiten ([docs/11](docs/11-verbesserungen.md)) und eine überarbeitete Roadmap ([docs/07](docs/07-roadmap.md)).
- `Analyzer.VERSION` 15: Analysen enthalten `coverage[]`, die Kategorie Tests hat die Ansicht `view: "tests"`; gespeicherte Analysen werden neu berechnet.
- **Ganzes Repository ohne Spezifikation:** Beim Analysieren des ganzen Repositorys gibt es keinen Spec-Diff – ohne Basis wäre jeder Test «neu» (`Analyzer.VERSION` 17).
- **Nie mehr Cache leeren nach einem Update:** `index.html` wird bei jedem Laden neu geprüft (`no-cache`), die gehashten JS-, CSS- und Schriftdateien sind unveränderlich und werden ein Jahr gecacht, API-Antworten nie. Das Favicon steckt direkt im `index.html`, es gibt keine ungehashte Datei mehr, die die Seite braucht.
- **Analyse viel schneller bei vielen Segmenten:** Die Import-Prüfung zwischen zwei Dateien wird pro Datei zwischengespeichert statt für jedes Paar von Segmenten neu gerechnet (eigenes Repo als Ganzes: 29 s → 2,5 s, Ergebnis identisch).

## [0.5.0] – 2026-11-13

### Neu
- **Generierte OpenAPI-Clients:** Die OpenAPI-Verträge des Repos werden gelesen; Frontend-Aufrufe generierter Services (`playersService.updatePlayer(…)`) werden über die operationId mit dem Controller verbunden, der das generierte `…Api`-Interface implementiert (oder einem Endpunkt mit passendem Pfad). Flows laufen so auch ohne URL im Code vom Browser ins Backend.
- **Schichten mit Adaptern (Onion-Stil):** Repos mit `domain` / `application` / `adapter` ohne Ports werden als «Schichten mit Adaptern» erkannt und bekommen die Architektur-Kategorien. Adapter werden nach Rolle gruppiert: eingehend (REST, Messaging-Listener, Fehlerbehandlung), ausgehend, Mapping, Konfiguration.
- **Neue Kategorien:** *API-Verträge* (Sprünge zu Aufrufern und Implementierungen der geänderten Operation), *Sicherheit & Berechtigungen*, *Messaging & Events*, *Transaktionen & Nebenläufigkeit*, *Datenbank & Migrationen* (Migration und Entity derselben Tabelle in einer Gruppe, mit Verweisen), *Konfiguration, Build & Betrieb*. Querschnitts-Kategorien kommen aus der neuen Regel-Liste `concerns`.
- **Auslöser im Flow-Titel:** `JMS-Listener: onMessage → …`, `PUT /rest/players/{}: updatePlayer → …`.

### Geändert
- Migrationen, JPA-Entities, Repositories mit Queries, `application.properties`, Dockerfile/CI/Deployment und Abhängigkeiten sind keine Quick wins mehr. Generierte Bäume (`gen/`, `dist/`, `build/generated/`) sind es neu.
- Message-Listener in `adapter/messaging/` gelten als eingehende Adapter (vorher: ausgehend). `infra/` unter `deploy/` zählt nicht mehr als Adapter-Schicht.
- Sprünge in Dateien ohne Symbole (YAML, SQL) werden angezeigt.

## [0.4.0] – 2026-11-13

### Neu
- **Ports & Adapters:** Das Repository wird anhand seiner Ordner (`domain`, `application`, `port`, `usecase`, `adapter`, `infrastructure` …) geprüft. Ist es so aufgebaut, bekommt jede Klasse eine Schicht und es gibt die Kategorien *Domäne*, *Use Cases*, *Application Layer* und *Adapter* (eingehend / ausgehend).
- **Frontend-Kategorien:** Routing & Navigation, Zustand & Stores, API-Anbindung, Formulare & Validierung, Komponenten-Logik, Templates & Markup (Regeln in `rules.json` → `aspects`).
- **Kategorien ein-/ausschalten** (Übersicht, Review-Baum). Ausgeschaltete Kategorien sind ausgeblendet und brauchen kein Ok; gespeichert in `<data>/settings.json`, API `GET/PUT /api/settings`.
- **Flows über REST:** HTTP-Aufrufe im Frontend (`http.put('/api/players/${id}')`, `fetch`, axios) werden mit Backend-Endpunkten verbunden (JAX-RS, Spring, Next.js-Route-Handler, Express, Go). Ein Flow läuft so von der Komponente über den API-Client ins Backend.
- **Komponentendiagramm** auf der Übersicht: alle geänderten Komponenten in Spalten nach Schicht, Aufrufe und REST-Aufrufe dazwischen, Fokus-Knopf pro Komponente.
- **Fokus im Flow-Diagramm:** Der Knopf im Knoten zeigt nur noch diesen Knoten und alles, was davon abhängt – im Diagramm und im Code.
- **Deutlichere Gestaltung:** Jede Verbindung in einem Flow hat ihre eigene Farbe (Diagramm, Verbindungslinie, Aufruf-Chip, «aufgerufen von»); REST-Verbindungen gestrichelt. Jeder Block und jeder Knoten zeigt seine Schicht (Frontend, API, Use Case, Application, Domäne, Daten, Test) als farbigen Streifen und Badge sowie die Sprache (TS, Java, Go, …); Frontend-Code ist zusätzlich leicht getönt. Die Verbindungslinien links neben dem Code laufen auf eigenen Spuren (mind. 11 px Abstand, lange aussen, kurze innen, Punkt an der Aufrufstelle, Pfeil am Ziel); der Rand wächst mit der Zahl der Spuren. Verschachtelte Aufrufe sind stärker eingerückt, tiefe Flows scrollen seitlich. Im Komponentendiagramm haben Spalten, Knoten und Verbindungen die Farbe ihrer Schicht.

### Geändert
- `analysis.json`: neue Felder `architecture`, `components`, `componentEdges`, `segments[].layer`, `segments[].frontend`, `flows[].edges[].kind`. Bestehende Analysen werden neu berechnet; neue Datei `structure.json` pro PR (Ordner des Repos).
- Regeln: `aspects`, `extras`, `text`, `fileText`, `special: "markup"`.

## [0.3.0] – 2026-11-13

### Neu
- **Tests ↔ Code:** Testdateien werden in Testfälle zerlegt (`describe`/`it`/`test`, JUnit `@Test`, Go `TestXxx`). Jeder geänderte Testfall zeigt die getesteten Komponenten und die abgedeckten Codestellen (direkt oder indirekt über andere geänderte Funktionen), statisch ermittelt. Neue Testübersicht in der Kategorie *Tests*, im Code «Getestet von …» / «Testet …».
- **Mehrere Orte, mehrere Oks:** Ein Block kann in mehreren Kategorien/Flows erscheinen und braucht dann an jedem Ort ein eigenes Ok. Leiste «n Orte» im Block-Kopf mit Sprüngen; Dateiansicht zeigt pro Zeile, wie vielen Orten sie zugewiesen ist (Häkchen dort gilt für alle Orte).
- **Fokus-Werkzeuge:** Blöcke einzeln ein-/ausklappen, alle ein-/ausklappen, «Einzeln durchgehen» mit «Ok & weiter»; im Flow zusätzlich Schritte aus-/einblenden, Erledigte ausblenden und «nur dieser Zweig».
