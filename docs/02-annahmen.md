# Annahmen und Vereinfachungen

Es handelt sich um einen PoC. Die folgenden Punkte sind bewusst einfach gehalten; jeder ist ein Kandidat für später.

## Produkt

| # | Annahme / Vereinfachung | Konsequenz |
|---|---|---|
| A1 | **Ein Benutzer, lokal.** Kein Login im Tool; der GitHub-Token kommt aus `GITHUB_TOKEN`/`GH_TOKEN` oder `gh auth token`. | Wer das Tool startet, handelt mit seinem eigenen GitHub-Konto. Der Server hört nur auf `127.0.0.1`. |
| A2 | **«Ok» ist der einzige Zustand** einer Zeile (markiert / nicht markiert) – pro Ort, an dem die Zeile erscheint (siehe B7). | Kein «braucht Nacharbeit», kein «unklar». Das Format lässt Erweiterungen zu (siehe Roadmap). |
| A3 | **Nur geänderte Zeilen** (hinzugefügt oder gelöscht) sind markierbar. Kontextzeilen werden nur angezeigt. | Fortschritt = markierte / geänderte Zeilen. |
| A4 | **Markierungen hängen an der Zeilennummer** (`N<neu>` / `O<alt>`) des Snapshots, nicht am Inhalt. | Ändert sich der PR (neue Commits), können Markierungen auf falsche Zeilen zeigen. Neue Commits sind laut Auftrag out of scope. «Von GitHub neu laden» behält die Markierungen bewusst unverändert. |
| A5 | **Kommentare werden sofort veröffentlicht** (einzelne Review-Kommentare, kein «Pending Review»). | Kein Sammeln, kein Approve / Request changes aus dem Tool. |
| A6 | Kommentieren geht nur auf **Zeilen, die im GitHub-Diff liegen** (geänderte Zeilen und deren 3 Kontextzeilen). | Zeilen ausserhalb (z. B. aus der Funktionsansicht) haben keinen Kommentar-Knopf; GitHub würde sie ablehnen. |
| A7 | **Markdown** in Kommentaren und PR-Beschreibung wird als Text angezeigt, nicht gerendert. | Gut lesbar, aber ohne Formatierung. |
| A8 | Nur **Dark Theme** (IntelliJ New UI «Dark»). | Kein Light-Mode-Umschalter. |
| A9a | **GitLab:** «Review-Anfragen» = offene MRs mit mir als *Reviewer* (`reviewer_username`), «Von mir» = `scope=created_by_me`. MRs, bei denen ich nur *Assignee* bin, erscheinen nicht. | In Teams, die Assignees statt Reviewer nutzen, fehlen MRs in der Liste (per URL öffnen geht immer). |
| A9b | **GitLab-Gruppen** werden in Referenzen, URLs und Ordnernamen als `gruppe~untergruppe` geschrieben (z. B. `reviews/gitlab/acme~platform/shop/7/`). | Pfade bleiben eine Ebene tief und dateisystemtauglich. |
| A9c | **Ohne GitLab-Token** lassen sich öffentliche MRs lesen (per URL), aber weder auflisten noch kommentieren. Ein GitLab-Self-managed-Server pro Instanz (`SCR_GITLAB_URL`). | Mehrere GitLab-Instanzen gleichzeitig sind nicht vorgesehen. |
| A9 | **Review-Anfragen an Teams** werden über die GitHub-Suche `review-requested:@me` gefunden – nur direkte Anfragen sind sicher abgedeckt. | Team-Reviews können fehlen. |
| A10 | Pro Suche **max. 100 PRs**, pro PR **max. 3000 Dateien** (GitHub-Limit), Dateien > 1 MB werden nicht geladen. | Genügt für normale Reviews. |
| A11 | **Commit-Zuordnung** über die First-Parent-Kette des Heads. Commits aus gemergten Seitenzweigen werden dem Merge-Commit zugeschlagen, Zeilen aus einem hineingemergten Basis-Branch bleiben ohne Commit. Höchstens 250 Commits (GitHub-Limit). | Bei verzweigter Historie sind einzelne Zeilen nicht oder nur dem Merge zugeordnet; der Gesamt-Diff ist davon nicht betroffen. |

## Analyse

| # | Annahme / Vereinfachung | Konsequenz |
|---|---|---|
| B1 | **Kein echter Parser**, sondern ein kleiner Lexer (Strings/Kommentare ausblenden, Klammern zählen) plus reguläre Ausdrücke. Unterstützt C-artige Sprachen: TypeScript/JavaScript, Java, Kotlin, C#, Go (grob). | Funktioniert für üblichen Code; exotische Syntax (Regex-Literale mit Klammern, verschachtelte Generics über Zeilen) kann Grenzen verschieben. |
| B2 | **Aufrufe = Namensübereinstimmung**: Funktion A «ruft» B auf, wenn der Name von B im Rumpf von A vorkommt. Über Dateigrenzen nur mit Import-Beleg (Modulpfad, Klassen- oder Funktionsname im Import); bei klassischen `<script>`-Dateien ohne Module gilt der globale Scope. | Gleichnamige Funktionen können falsch verbunden werden; dynamische Aufrufe (Reflection, DI per String, Events) werden nicht erkannt. |
| B3 | **Nur geänderte Funktionen** bilden Flüsse. Unveränderte Zwischenstationen werden nicht eingeblendet. | Ein Fluss A → (unverändert X) → B erscheint als zwei getrennte Teile. |
| B4 | **Hubs**: Wird eine Funktion von mehr als 5 geänderten Stellen aufgerufen (z. B. `cn`, `Button`), gilt sie als gemeinsames Hilfsmittel und verbindet keine Flüsse. | Bei sehr grossen PRs (ganze neue Website) bleiben einzelne Flüsse trotzdem gross (bis ca. 80 Schritte); dafür gibt es die Fokus-Werkzeuge. |
| B4a | **Ein Flow pro Einstiegspunkt.** Wird eine Funktion von zwei Einstiegspunkten erreicht, ist sie Teil beider Flows. In zusammenhängenden Gruppen mit mehr als 20 Funktionen gilt das nicht: dort erscheint jede Funktion nur im ersten Flow, der sie erreicht. | Normale Feature-PRs zeigen gemeinsame Funktionen in jedem Zusammenhang; riesige PRs werden nicht durch Duplikate aufgebläht. |
| B5 | **Einstiegspunkt** eines Flows = Funktion ohne Aufrufer innerhalb des Flows; bei mehreren gewinnt die «äusserste» Schicht (Pfad enthält `component`, `page`, `controller`, `resource` … vor `service` vor `repository`, `client`, `utils`). | Heuristik; die Reihenfolge ist meist plausibel, aber nicht garantiert. |
| B6 | **Quick wins nach Regeln** (`rules.json`): zuerst Pfad-Regeln für ganze Dateien, dann Zeilen-Regeln pro Segment («alle geänderten Zeilen sehen aus wie Feldzuweisungen» usw.). Die erste passende Regel gewinnt. | Regeln sind bewusst konservativ; im Zweifel landet Code bei der Logik. |
| B7 | **Mehrere Orte, mehrere Oks.** Ein Block kann an mehreren Orten erscheinen (Quick win *und* Flow-Schritt, oder in zwei Flows). Jeder Ort braucht ein eigenes Ok, weil man denselben Code in einem anderen Zusammenhang anders liest. Eine Zeile gilt als erledigt, wenn sie an allen Orten ok ist. | Der Gesamtfortschritt zählt Zeilen (erst ok, wenn überall ok); Kategorie- und Flow-Fortschritt zählen pro Ort. |
| B7a | **Dateiansicht und Agenten markieren überall.** Ein Häkchen in der Dateiansicht (und eine Markierung ohne `place` über API/Datei) gilt für alle Orte der Zeile. | Wer dateiweise reviewt, muss nicht jeden Ort einzeln besuchen. |
| B7b | Orte sind die **Gruppen-IDs der aktuellen Analyse**. Ändern sich Regeln so, dass Gruppen anders heissen, verlieren ortsbezogene Teil-Markierungen (`okAt`) ihren Bezug; vollständige Markierungen (`ok`) bleiben gültig. | Bei Regeländerungen ggf. einzelne Orte neu bestätigen. |
| B8 | **Frontend ↔ Backend über REST:** Ein HTTP-Aufruf mit **literaler** URL (auch Template-Strings mit Parametern, `'/x/' + id`, `${base}/x`) wird mit einem Endpunkt verbunden, wenn Methode und Pfad passen (Parameter passen auf alles, ein Basis-URL-Parameter am Anfang darf mehrere Segmente abdecken). Endpunkte: JAX-RS (`@Path` + `@GET` …), Spring (`@GetMapping` …), Next.js `app/**/route.ts` und `pages/api`, Express/Fastify `app.get('/x')`, Go `HandleFunc("PUT /x")`. | URLs aus Konstanten oder Konfiguration, GraphQL und WebSockets werden nicht erkannt (generierte OpenAPI-Clients: siehe B19). Unit-Tests folgen REST-Kanten nicht (HTTP ist dort gemockt). |
| B9 | Die Quelltexte der **neuen Version** werden einmal beim Öffnen geladen (nur Dateien, die analysiert werden, inkl. Testdateien). Für gelöschte Dateien gibt es nur den Diff. Fehlen Quelltexte, die neue Regeln brauchen, werden sie bei der nächsten Analyse nachgeladen. Ausnahme: Von **geänderten, umbenannten und gelöschten Testdateien** wird zusätzlich die **alte Version** am Basis-Commit geladen (`sources-base/`, bei umbenannten unter dem alten Pfad), für die Spezifikation der Testnamen (B12a); bei älteren Snapshots einmal bei der nächsten Analyse. Zweite Ausnahme: **bestehende, unveränderte Testdateien**, die den geänderten Code wohl testen (B11a), werden am Head-Commit geladen (`sources-related/`), bei der ersten Analyse nach dem Laden bzw. bei älteren Snapshots bei der nächsten. | Gelöschte Funktionen erscheinen als Hunk-Segment ohne Namen. Der Basis-Commit ist der Stand beim Laden des PRs; wurde der Ziel-Branch seither weiterentwickelt, vergleicht die Spezifikation trotzdem mit dieser Basis. Schlägt das Laden fehl, zeigt sie nur die neue Seite. |
| B10 | **Testabdeckung ist statisch**: Ein Testfall «deckt» eine geänderte Codestelle ab, wenn er sie (über denselben Aufruf-Graphen wie die Flows) aufruft – direkt, über Test-Hilfsfunktionen in der Testdatei, oder indirekt über andere geänderte Funktionen (bis 4 Ebenen). Tests werden nicht ausgeführt, keine Laufzeit-Coverage. | Aufrufe über HTTP (`given().put("/api/…")`), Templates, Events oder DI per String werden nicht erkannt. Unveränderter Code zwischen Test und Änderung unterbricht die Kette (wie B3). |
| B10a | **Abdeckung aus Sicht des Codes** (`coverage[]`) ist ebenso statisch: Eine testbare geänderte Funktion (Funktion/Methode/Komponente, deren Kategorie `needsTests` hat) ist «direkt getestet», wenn ein **geänderter** Test sie aufruft, «nur indirekt», wenn er sie nur über anderen geänderten Code erreicht, «nur durch bestehende Tests», wenn kein geänderter, aber ein nachgeladener bestehender Test sie erreicht (B11a), sonst «ohne Test». Verzweigungen werden auf dem Code ohne Strings/Kommentare gezählt (`if`, `case`, `catch`, `for`, `while`, `&&`, `\|\|`, ternäres `?`). | Unveränderte Tests zählen nur, wenn ihre Datei nach Namen gefunden wurde (B11a) – «ohne Test» heisst «kein geänderter und kein gefundener bestehender Test erreicht sie», nicht «ungetestet». Aufgerufen heisst nicht, dass jeder Zweig geprüft ist. Von Frameworks aufgerufene Methoden (`ngOnInit`, `render` …) fehlen, ebenso triviale Getter/Setter (Rumpf nur `return x;` bzw. `this.x = x;`). |
| B10b | **Mock-Grenzen** sind namensbasiert: Eine geänderte Funktion gilt in einem Test als **gemockt**, wenn die Klasse, in der sie steht (bzw. ihr Dateiname ohne Endung oder ihr eigener Name bei Klassen/Komponenten), unter den Mocks des Steckbriefs steht (B12c) – verglichen ohne Gross-/Kleinschreibung und Satzzeichen (`PlayerApiService` = `player-api.service`). Die Verknüpfung (B10) hält dort an, und gemockt Erreichtes zählt nicht als Abdeckung. Eine **Warnung** gibt es, wenn der Test eine geänderte Funktion einer gemockten Abhängigkeit beim Namen stubbt oder nennt (`m: jest.fn(`, `createSpyObj('X', ['m'])`, `spyOn(x, 'm')`, `when(repo.m(`, `verify(repo).m(`, `.m`; Regeln `testProfile.mockMembers`). Eine Flow-Verbindung gilt als durchlaufen, wenn ein Test beide Enden echt erreicht; HTTP-Verbindungen nie (Regeln in [05-analyse.md](05-analyse.md), Abschnitt 5g). | Gemockt wird pro Klasse, nicht pro Methode: `spyOn(obj, 'm')` gilt für die ganze Klasse, und Spione, die den echten Code aufrufen (Jest `spyOn` ohne Implementierung, Mockito `@Spy`), zählen trotzdem als Mock. Der Memberzugriff `.m` kann eine gleichnamige Methode eines anderen Objekts treffen. Mocks aus Hilfsfunktionen anderer Dateien fehlen (wie B12c). |
| B11 | **Getestete Komponenten** = Namenskonvention (`PlayerResourceTest.java` → `PlayerResource.java`, `a.service.spec.ts` → `a.service.ts`, `x_test.go` → `x.go`) plus die Dateien/Klassen, die der Test direkt aufruft. Passt keine Datei im PR, wird der Name trotzdem genannt («nicht im PR geändert»). | Heuristik; bei unüblichen Namen fehlt die Namens-Komponente. |
| B11a | **Bestehende Tests** (Stufe A, Regel-Abschnitt `relatedTests`): Dieselbe Namenskonvention gilt rückwärts. Zu jeder geänderten Quelldatei werden bestehende Testdateien aus der Dateiliste des Repositorys gewählt – nach ihr benannt im gespiegelten Testordner (`src/main/` → `src/test/` …) oder daneben, sonst die nächstgelegene gleichen Namens anderswo, dazu Testdateien im gespiegelten Ordner, deren Name mit ihrem beginnt (`PlayerResourceSecurityTest`). Höchstens 30 pro PR, nicht beim ganzen Repository. Ihre Testfälle werden wie geänderte verknüpft, sind aber keine Segmente (Regeln in [05-analyse.md](05-analyse.md), Abschnitt 5f). | Nur Namen: Tests mit anderem Namen fehlen (ein Index über alle Tests ist Stufe B). Tests, die den Code nur über HTTP oder das Rendern einer Komponente erreichen, verknüpfen sich nicht. Gekürzte Dateilisten (GitHub `truncated`, GitLab max. Seiten) können Treffer verlieren – das UI warnt. |
| B12 | **Testfälle** werden erkannt als `describe/it/test(…)`-Blöcke (JS/TS, inkl. `.only/.skip/.each`), JUnit-Methoden mit `@Test`/`@ParameterizedTest` …, Go-Funktionen `TestXxx`/`BenchmarkXxx`/`FuzzXxx`. Nur **geänderte** Testfälle erscheinen. | Python-Tests und andere Frameworks werden als Hunks gezeigt, ohne Verknüpfung. |
| B12a | **Spezifikation (Spec-Diff):** Die Testnamen jeder geänderten Testdatei werden als Gliederung (Suite › Test) mit der Basisversion verglichen – auch unveränderte Tests derselben Datei. JUnit: Testklasse und `@Nested`-Klassen sind Suites, der Name ist der Methodenname. Gleicher Pfad = derselbe Test; gleicher Text ohne Leerraum und Namen = umbenannt (Regeln in [05-analyse.md](05-analyse.md), Abschnitt 5b). | `@DisplayName`, Go-Subtests (`t.Run`) und dynamisch erzeugte Namen werden nicht ausgewertet. Name **und** Inhalt geändert = «entfernt» + «neu». |
| B12b | **Geänderte Erwartungen** sind musterbasiert (Regel-Abschnitte `assertions`, `weakAssertions`, `disabledTests`): Assertion-Anweisungen im Testrumpf werden alt gegen neu gepaart – identisch, sonst über den geprüften Gegenstand (`expect(x)`, `assertThat(x)`, bei `assertEquals(erwartet, tatsächlich)` das zweite Argument). Gleicher Gegenstand mit anderem Wert = «Erwartung geändert», Wechsel zu einem reinen Existenz-/Wahrheitstest = «abgeschwächt»; `xit`, `.skip`, `@Disabled`, `t.Skip` = «deaktiviert», auch über die umschliessende Suite (Regeln in [05-analyse.md](05-analyse.md), Abschnitt 5c). | Heuristik: Assertions in Hilfsfunktionen oder `beforeEach` und erwartete Werte in Variablen (`want := 3`) werden nicht gesehen; Frameworks ohne passendes Muster zählen null Assertions. JS `assert.equal(actual, expected)` wird über das erste Argument gepaart. Ein bedingtes `t.Skip` (in einem `if`) zählt nicht als deaktiviert. |
| B12c | **Test-Steckbrief** pro geändertem Testfall, musterbasiert (Regel-Abschnitt `testProfile`): Fehlerfall, wenn der Test ein Scheitern erwartet (`assertThrows`, `.toThrow`, Stub wirft, HTTP-Status ≥ 400, Prüfung einer Fehlermeldung) oder der Name es sagt (*rejects, invalid, not found, ungültig* …, nicht nach *not/no/kein*); Grenzfall bei Namen wie *empty, null, max, leer, Grenze* oder `null`/`""`/leeren Sammlungen in den **Eingaben des geprüften Codes** (Argumente der Aufrufe der direkt aufgerufenen geänderten Funktionen und von HTTP-Anfragen, `@NullSource`/`@EmptySource`, `@ValueSource`/`@CsvSource`, `it.each`- und Go-Tabellen) – nicht in Testdaten, Setup oder erwarteten Werten; Ebene aus Annotationen (`@QuarkusTest`, `@SpringBootTest`, Testcontainers), RestAssured/MockMvc und Pfad (`e2e/`, `*IT.java`); Angular-`TestBed` mit gemocktem Backend bleibt Unit. Mocks aus Test, Setup und umschliessenden Klassen/Suites; parametrisierte Fälle aus `@ValueSource`/`@CsvSource`, `it.each`, Go-Tabellen (Regeln in [05-analyse.md](05-analyse.md), Abschnitt 5d). | Heuristik: Zahlen an Grenzen (0, 100) werden nicht erkannt; eine `null`-Eingabe über eine Variable (`const x = null; valid(x)`) oder über eine Hilfsfunktion wird nicht gesehen; ohne Aufruf eines Ziels kommt ein Grenzfall nur aus Name oder Parameterquelle; Tabellentests mit gemischten Zeilen bekommen einen Fall für alle Zeilen. `@MethodSource` und `it.each(variable)` haben keine Anzahl. Mocks aus Hilfsfunktionen anderer Dateien fehlen. |
| B12d | **Fallmatrix** (Regel-Abschnitt `caseMatrix`): Tests derselben Suite einer geänderten Testdatei gelten als **ähnlich**, wenn ihr Eingabecode Token für Token gleich ist, sobald alle Literale (Zahlen, Strings, `true`/`false`, `null` …) maskiert sind; Assertions dürfen abweichen. Eingabe ist alles ausserhalb der Assertions plus das, was eine Assertion anschaut (`putJerseyNumber(7).then()` vor `.statusCode(200)`, `x` in `expect(x)`, das tatsächliche Argument von `assertEquals`); Erwartung ist der Matcher mit seinem Wert, ausgerichtet über die Eingabeseite mit maskierten Literalen. Spalten = Literale, die sich zwischen Tests unterscheiden; gleiche Eingabewerte = derselbe Fall doppelt (widersprüchlich bei anderer Erwartung). Parametrisierte Tests: die literalen Zeilen von `@ValueSource`/`@CsvSource`/`@EnumSource`/`@NullSource`, `it.each`, Go-Tabellen; eine Spalte ist Erwartung, wenn ihr Name danach klingt (`expected`, `want`, `status`, `message` …) oder sie nur in Assertions vorkommt (Regeln in [05-analyse.md](05-analyse.md), Abschnitt 5e). | Heuristik ohne Toleranz: ein zusätzlicher Aufruf trennt Tests, die man als ähnlich empfinden würde; Werte in Hilfsfunktionen oder in anderswo deklarierten Variablen sind unsichtbar (zwei Tests, die sich nur dort unterscheiden, gelten als doppelt); `if (got != 3) t.Errorf(…)` macht die 3 zur Eingabe; ein Parameter `status`, der eigentlich eine Eingabe ist (gemockte Server-Antwort), gilt wegen seines Namens als Erwartung. Keine Hinweise auf fehlende Grenzwerte – dafür müsste man den geprüften Code lesen. |
| B14 | **Ports & Adapters** gilt als erkannt, wenn die Ordner des Repos (GitHub: Git-Tree, GitLab: Tree-API, max. 3000 Einträge) sowohl eine Rand-Schicht (`adapter`, `infrastructure`, `port`) als auch eine Kern-Schicht (`domain`, `application`, `usecase`) enthalten. Die Schicht einer Datei ergibt sich aus dem Namen (`…UseCase` → Use Case, `…Service` unter `application/` → Application) und sonst aus dem tiefsten passenden Ordner; `adapter/in` bzw. `…/web`, `…/rest` = eingehend, `adapter/out`, `…/persistence` = ausgehend. | Geschichtete Projekte (nur `api` + `domain`) bekommen keine Architektur-Kategorien. Eigene Ordnernamen (z. B. `core`) werden nicht erkannt. Ordner unter `deploy/`, `terraform/`, `helm/` … zählen nicht (dort ist `infra` Infrastruktur-Code). |
| B14a | **Schichten mit Adaptern (Onion-Stil)** = `domain` + `application` + `adapter`, aber **ohne** `port`, `usecase` oder `adapter/in|out`: Stil «layered». Kategorien wie bei Ports & Adapters; Adapter werden nach Rolle gruppiert: eingehend (`rest`, `api`, `errorhandling`, `…Controller`, Message-Listener `…Listener/…Consumer`), ausgehend (`persistence`, `client`, `…Publisher`), Mapping (`mapping/`, `…Mapper`), Konfiguration (`configuration/`, `…Configuration`). Repository-Interfaces unter `domain/` gehören zur Domäne. `common/` bekommt keine Schicht. | Aufrufe laufen ohne Interfaces direkt (Konstruktor-Injektion) – genau das verfolgt die Namenssuche (B2). |
| B15 | **Frontend-Dateien:** `.tsx/.jsx/.vue/.svelte/.html` oder TS/JS in Frontend-Ordnern (`frontend/`, `src/app/`, `components/` …) bzw. mit Angular-/React-/Vue-Import; Backend-Pfade (`src/main/`, `server/`, Next.js-API-Routen) sind ausgenommen. Jedes Frontend-Segment bekommt **höchstens eine** Frontend-Kategorie (erste passende Regel in `aspects`). | Geteilte Utilities ohne passende Regel bekommen keine Frontend-Kategorie. |
| B16 | Architektur- und Frontend-Kategorien sind **eigene Orte mit eigenem Ok** (Entscheid). Quick wins der Arten Generiert, Übersetzungen, Imports, Formatierung, Logging, Doku, Konfiguration sowie Tests und Styles bekommen keine Zusatz-Kategorien (`"extras": false`). | Ein Backend-Block kann so 2–3 Oks brauchen; wer das nicht will, schaltet die Kategorien aus. |
| B17 | **Kategorien ausschalten** gilt global für alle PRs (`<data>/settings.json`). Ausgeschaltete Orte zählen nicht; Zeilen, die nur in ausgeschalteten Kategorien vorkommen, fallen aus dem Gesamtfortschritt (in der Dateiansicht bleiben sie sichtbar). | Wer z. B. «Tests» ausschaltet, ist ohne Test-Review bei 100 %. |
| B18 | **Komponenten** = geänderte Code-Dateien gleichen Namens im gleichen Ordner (`player-view.ts` + `.html` + `.scss`); Name = gleichnamige Klasse, sonst häufigste Klasse, sonst Dateiname. Spalten im Diagramm: Tests, Frontend, Adapter ein, API, Use Cases, Application, Logik, Adapter aus, Daten, Domäne (ohne Ports & Adapters nach Pfad-Heuristik). Verbindungen = zusammengefasste Aufruf- und REST-Kanten. | Nur geänderter Code erscheint; unveränderte Komponenten dazwischen fehlen (wie B3). |
| B19 | **Generierte OpenAPI-Clients und -Interfaces:** Verträge im Repo (`openapi*.yaml/json`, `swagger*`, `*.openapi.yaml`, max. 10) werden einmal pro Head gelesen (`structure.json`: `operations` mit operationId, Methode, Pfad inkl. `servers`-/`basePath`-Präfix, Zeilenbereich). Ein Frontend-Aufruf `x.updatePlayer(…)` mit dem Namen einer operationId wird zum REST-Aufruf dieser Operation; Gegenstück ist eine Methode gleichen Namens in einer Klasse, die ein generiertes `…Api`/`…ApiDelegate`-Interface implementiert, oder ein annotierter Endpunkt mit passendem Pfad. Ohne Vertrag genügt der Name, wenn das Frontend aus `/gen/`, `/generated/` oder `/api` importiert. Geänderte Zeilen im Vertrag springen zu Aufrufern und Implementierungen der Operation. Generierte Bäume (`gen/`, `dist/`, `build/generated/` …) sind Quick wins. | Ein gleichnamiger, selbst geschriebener Wrapper im Frontend nimmt dem Generat den Aufruf ab (die Kante läuft dann über den Wrapper). YAML wird zeilenweise gelesen, nicht vollständig geparst; `$ref`-aufgeteilte Verträge liefern nur die Operationen der Hauptdatei. |
| B20 | **Querschnitts-Kategorien** (`concerns` in `rules.json`): Sicherheit & Berechtigungen, Messaging & Events, Transaktionen & Nebenläufigkeit, Datenbank & Migrationen. Alle passenden Regeln zählen (nicht nur die erste); Bedingungen wie bei `aspects` plus `scope` (frontend/backend). Funktionen werden als Ganzes geprüft (inkl. Annotationen), Klassen nur mit Deklaration und geänderten Zeilen. Auch Konfigurationsdateien (`application.properties`, Terraform) bekommen so Security-, Messaging- oder Datenbank-Orte. | Muster-basiert: `@Transactional` an der Klasse statt an der Methode wird für die Methode nicht erkannt. Mehr Orte = mehr Oks; Kategorien lassen sich ausschalten (B17). |
| B21 | **Schema als Einheit:** Migrationen (`db/changelog/**`, `db/migration/**`, `*.sql`, Liquibase-Changelogs) und JPA-Entities (`@Entity`) sind nie Quick wins, sondern *Datenbank & Migrationen*. Nennen Migration (`tableName: x`, `create/alter table x`) und Entity (`@Table(name = "x")`, sonst Klassenname) dieselbe Tabelle, stehen sie in der Gruppe «Tabelle x» und verweisen aufeinander. Repository-Interfaces mit `@Query` bzw. `extends …Repository` ebenso. | Tabellennamen werden ohne `_` und Gross-/Kleinschreibung verglichen; abweichende Naming-Strategien werden nicht erkannt. |
| B22 | **Laufzeit statt Quick win:** `application*.properties/yml`, Logging-Konfiguration, Dockerfile, CI (`Jenkinsfile`, Workflows), Deployment (`deploy/`, Helm, Terraform, Argo CD) und Abhängigkeiten (`package.json`, `pom.xml`, `build.gradle` …) bilden die Kategorie *Konfiguration, Build & Betrieb*. Nur Werkzeug-Konfiguration (tsconfig, Linter, Editor) und Lockfiles bleiben Quick wins. | PRs mit vielen Versions-Bumps haben dort mehr zu prüfen als früher. |
